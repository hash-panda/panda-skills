# 评估协议

在决定实验、比较收益或判断是否推广时使用。下面是建议的工程方法，不代表已经运行的实验结果。

## 先定义“更好”

为一轮实验固定：

| 项目 | 需要记录 |
| --- | --- |
| 主指标 | 对用户/系统有价值的结果，单位与改善方向 |
| 基线 | 版本、时间窗口、样本/分母、任务难度、负载和原始来源 |
| 质量约束 | 成功率、正确率、隐私、可靠性、延迟等适用约束 |
| 变化 | 本轮真正要验证的因素及同时发生的其他变化 |
| 验收 | 阈值、比较方法、最短观察期或所需样本的依据 |
| 终止 | 预算、失败阈值、回退条件、待观察到何时 |

阈值优先采用已有业务要求；缺少时提供有理由的暂定标准，并与已确认目标区分。不得把建议阈值写成用户要求。
不要在看到结果后反复调阈值、换样本或延长实验，直到获得满意结论。
探索数据用于发现候选；保留后续任务、独立样本或可信用户反馈用于确认。不可直接把探索集最佳成绩当成泛化收益。

## 选择匹配的验证

| 变更类型 | 最小有意义的验证 | 不能据此声称 |
| --- | --- | --- |
| 已复现缺陷 | 原失败用例、正常路径及受影响的回归边界 | 全系统可靠性已提升 |
| 性能/成本 | 相同任务、负载、模型/配置或明确控制变量下比较 | 质量下降但成本下降就是成功 |
| 产品路径 | 目标人群的任务完成、行为或反馈；必要时分组对照 | UI 做完就提高了留存/收入 |
| 架构替换 | 小切片验证功能、负载、维护和迁移成本 | 小基准成绩代表全量 ROI |
| Agent 方法 | 相同资源条件下的基线/候选，使用未用于调参的任务 | 记忆命中旧题等于改进能力增强 |

一次修复可用确定性测试证明特定行为。开放式质量和业务效果通常需要更多任务或观察时间，按证据强度限定结论。
给出样本量、通过/失败数量、分母、条件差异和不确定性；有统计能力和足够数据时再给区间。小样本不输出虚假的精确显著性或总体提升率。
抽查原始执行结果与失败案例，保留失败、超时和无结果，避免只统计成功运行。

## 成本和价值

先看质量约束是否满足，再讨论成本收益。高价值探索允许短期成本增加，但需要目标、预算与可终止的验证计划。

在同一观察期内考虑：

- 模型调用、计算、存储、外部服务费用。
- 实现、评审、测试、维护、迁移与运行成本。
- 用户学习/切换、失败返工和人工兜底。
- 可被证据支持的节省、价值或收益；未确认需求只能写成假设。

只有收益与成本能可靠折算为同一货币单位时，才计算：

`ROI = (该观察期内增量收益 − 增量总成本) / 增量总成本`

注明口径、时间、估算依据和范围；成本为零时不要使用该公式。
无法货币化时直接列出成功率、完成时间、单位任务成本、人工介入率等原始量，不把异质指标随意加权成“ROI 分”。

## 评估的独立性

评审者可以帮助发现盲点；另一个 Agent 的主观认可不能作为唯一验收。
将评估标准、参考答案、保留用例与候选实现分开；实现者可以查看开发测试，不能修改独立验收来消除失败。
如果发现验收用例本身错误，记录问题与修订理由，保留旧结果，重新建立可比较条件。
必须报告验证了哪一层：格式正确、指令被执行、技术行为成立、用户结果改善、跨任务迁移成立。后一层不由前一层自动推出。

## 最终决策

- **成立**：达成事先约定的目标，且约束满足；注明适用任务和观察窗口。
- **未成立**：目标未达成，或任一必要约束失败；按约定停止、回退或重新提出假设。
- **待观察**：技术工作完成但业务效果未成熟，或证据不足以作判断。
- **无需变更**：现状满足目标，或没有成本合理且有证据支持的候选；记录复查触发条件。

结果成立也不自动扩大发布范围。按用户和项目已经给出的范围交付，无须重复请求已经明确的授权。
