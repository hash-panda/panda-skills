## 执行前固定的实验协议

**可证伪假设 H1：** 对同一版本、同一 Node 环境、相同的有效事件 `{tenantId: "alpha", eventId: "evt-restart", payload: "first"}`，仅将两次投递从同一实例改为先后两个全新进程，累计新建数仍为 1 且第二个进程新增数为 0；否则，上轮方案不满足重启后的新要求。

- 对照版本与候选版本均为未经修改的上一轮 `queue.ts`。本轮改变的是生命周期条件，没有产品实现变更。
- 原范围验证固定为现有 31 项测试，一次执行，保存完整 TAP 和退出码。
- 接续复现固定为 2 项测试：同一实例投递两次的阳性对照，以及相同事件分别在两个先后运行、正常退出的真实 Node 子进程中各投递一次。后者不是在同一进程中仅清空数组或重新赋值。
- 新要求的样本/分母为 1 个租户事件组合、2 次投递、2 个先后进程、1 次重启边界；对照也是 1 个组合、2 次投递，但使用 1 个实例。不能把这次确定性反例转化为生产故障率。
- 新建数由每次 `enqueue` 前后 `jobs.length` 的差值观测并累计。两个进程都返回 `id: 1` 不代表恢复了首次任务，因为该 id 本身来自每个空数组的局部长度。

- **原结论仍成立，范围不变。** 同一 Queue 实例内的去重、完整输入验证、身份隔离和首次 payload 语义，由本轮原样运行的 31/31 再次确认。重启失败不否定上轮在其明确范围内的结论。

## 方案取舍与下一步回路

当前轮选择补证据并保留反例，至此完成。本轮没有产品代码改动。后续满足新需求属于**结构改进**：被挑战的是“身份与任务的有效期只需覆盖一个 Queue 实例”这个原有假设，而不是数组查找性能。

| 候选 | 价值、证据、成本与不确定性 | 决策 |
| --- | --- | --- |
| 保持现状并记录边界 | 无实现成本；新要求已有直接失败证据 | 适合作为本轮有界诊断结果，不能作为新要求的最终解决方案 |
| 数组改 Map、模块级缓存或稳定编号 | 能改变查找成本、进程内共享或编号表现，但不保留退出进程的身份事实 | 不做；局部数据结构调整不足以解决本次失败 |
| 只保存去重标记或退出时导出快照 | 有机会通过部分正常重启情形，但“已标记却未创建”与“已创建却未标记”两次写入窗口、非正常退出与恢复语义尚未解决 | 不作为首选；避免先承诺超出证据的可靠性 |

## 下一轮最小实验（设计，未执行）

### 假设、最小切片与固定口径

**可证伪假设 H2：** 对显式的同一逻辑队列空间，在首次任务及 `(tenantId, eventId)` 身份通过同一次原子、可恢复写入提交后，进程结束或在提交后响应前终止，下一进程重新打开同一空间并投递同一事件，将返回相同的稳定任务标识与首次 payload，不发生第二次已提交创建；身份隔离和输入验证保持通过。若出现重复创建、首次任务丢失、payload 被覆盖或合法新事件被误抑制，则 H2 不成立。

1. 选一个支持本地可恢复写入及唯一约束的最小后端，先确认运行环境已有能力；无需为实验创建外部服务。本轮没有选型完成、后端可用或持久性等级已验证的证据。
2. 将身份范围显式写为 `(logicalQueueId, tenantId, eventId)`。本轮任务可合理推定“重启同一服务”沿用同一 logicalQueueId；独立逻辑队列仍相互隔离。这是拟议的契约具体化，不是已知的生产配置。
3. 单个任务记录同时承载唯一身份、稳定任务标识和首次 payload。执行完整输入校验后，进行原子的“创建或取回”，在提交成功后才确认接收。避免把去重标记与任务创建分成两个独立提交；仅用原子唯一任务记录即可检验所需切片，不另做执行器或投递系统。
4. 新旧实现使用相同 Node 版本、相同有效/无效输入；本轮失败测试和日志作为不可覆盖的旧基线。为候选单独建测试文件与结果目录，不能把旧复现改成通过后覆盖失败历史。
5. 对候选使用持久记录的成功插入计数及重新打开后的记录查询作为主要证据，不能只检查返回 id 或内存数组长度。每个成功接收的身份最终恰有 1 条任务记录；重复投递新增记录数为 0。跨进程比较稳定标识和字段，不比较对象引用。

### 预设验收矩阵

新增固定为下列 8 个确定性场景，每个执行 1 次；涉及终止的场景使用显式故障注入点，不依赖随机 sleep 碰巧命中。正常重启场景 R1 使用 3 个先后进程、同一身份共 3 次投递，包含 2 次重启边界。其余场景按表格固定输入和进程边界，所有失败、超时均保留。

| 编号 | 条件 | 验收 |
| --- | --- | --- |
| R1 | 首次提交并确认后，正常退出；后续 2 次启动均重投同一事件 | 3 次返回的稳定任务标识一致；累计已提交创建 1；重启后每次新增 0 |
| R2 | 首次 payload 为 `first`，重启后相同身份传 `replacement` | 返回首次标识及 `first`；任务仍为 1 条 |
| R3 | 同一空间，首次 `alpha/evt-1`；重启后 `beta/evt-1`，再重投 `alpha/evt-1` | 共 2 条任务，租户互不影响；最后一次新增 0 |
| R4 | 同一空间，首次 `alpha/evt-1`；重启后 `alpha/evt-2`，再重投 `alpha/evt-1` | 共 2 条任务，事件互不影响；最后一次新增 0 |
| R5 | 合法任务提交并重启；相同身份投递空 payload | 抛出原输入错误；首次标识与 payload 不变；没有新增记录 |
| R6 | 在任务原子提交后、返回/确认前终止进程；重启并重投 | 恢复已有记录；累计提交创建 1；不得因为首次响应丢失再次创建 |
| R7 | 在原子提交前的注入点终止进程；重启并重投 | 恢复后没有半条身份/任务；重投最终创建 1 条；无“标记存在却任务不存在” |
| R8 | 同一存储、两个显式不同的 logicalQueueId，各投相同租户/事件并分别重启重投 | 每个空间 1 条，各自重投不新增；不同空间不误去重 |

继承质量约束另列而不混淆分母：旧实现继续保留原 31 项及结果；候选必须原样复用可适用的 30 项行为约束，另以显式不同逻辑队列空间重建第 7 项“独立实例”测试的隔离意图，形成 31 项候选兼容检查。第 7 项的映射变化来自新的生命周期契约，必须在候选实现前记录，不能在结果失败后偷偷删测试或把两个代表同一服务的启动解释成两个独立空间。候选验收分别报告“兼容检查 31/31”和“重启场景 8/8”，不得只报告合并通过率。
